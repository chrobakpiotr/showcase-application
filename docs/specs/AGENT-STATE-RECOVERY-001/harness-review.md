# AGENT-STATE-RECOVERY-001 — Harness review packet

**Status:** Harness accepted with amendments in `agent-harness` commit `2b5ee6a`. Implementation is in progress; no recovery write is authorized until Harness reviews the implementation.

## Decision and objective

Showcase accepts that the old `SDD-OBS-001` outer lifecycle authority cannot be reconstructed exactly. Do not reset or migrate the absent state, and do not infer historical packet revisions, attempts, replans, or retry grants from ordinary evidence. Establish a separately identified, explicitly authorized new lifecycle epoch. Preserve the surviving evidence unchanged and revalidate every completion that the new epoch imports. `T-009` must be evaluated from scratch against the current implementation and accepted criteria.

The scope is the task lifecycle authority under repository `.agent-state`. It does not restore or alter the distinct verifier control store under `.agent-runs/control/verification-v2`.

## Incident facts recorded for review

- `.agent-state` was absent at the Showcase checkout during the 2026-10-11 investigation. The owner reported no APFS/Time Machine snapshot or other on-disk copy.
- No mutating lifecycle command was run during this investigation. A read-only `harness.py status --json` returned an in-memory all-pending projection and left `.agent-state` absent.
- `initial_state()` only projects C1/C2 completion authority if that authority is readable. It does not recover the missing packet revisions, attempt/replan lineage, or human-resolution history. `migrate-state` explicitly refuses to create absent authority.
- The prior T-009 completion evidence is not sufficient for import: Harness's round-4 review rejected that implementation. The currently present attempt-6 completion file is untracked. T-009 therefore requires fresh evaluation and cannot be imported as completed.
- `evidence-baseline.json` records byte hashes and Git tracking status for the surviving `SDD-OBS-001/evidence/` tree at proposal time. Its untracked entries are preserved locally but are not authoritative completion records.

## Proposed recovery contract

1. **Explicit incident record.** Before any recovery write, require an operator-attributed, immutable record bound to repository identity, current feature fingerprint, the evidence-baseline digest, the missing-state observation, a new epoch ID, and the explicit statement that old packet-revision/attempt history is unavailable. Unknown cause stays `unknown`; the tool must not invent a cause.
2. **Fail closed by default.** Read-only inspection stays read-only. Every ordinary mutating lifecycle command refuses when authority is missing. Only the explicit recovery command may create a new epoch, and it requires the incident record and operator attribution. It never acts as `reset` or `migrate-state`.
3. **Byte-preserving evidence.** Recovery may only add new records in a separate recovery namespace. Before and after recovery, verify each pre-existing evidence path against the baseline hash; a missing, modified, or newly overwritten prior file blocks recovery. Human-resolution artifacts remain historical and do not become active retry grants.
4. **No implicit completion import.** A completion is imported only after an independent evaluator revalidates the exact checkpoint against the current accepted task contract and current code, with a newly materialized packet revision and evidence bound to the new epoch. Failed, stale, untracked, or unverifiable records remain archival evidence. `T-009` always gets a fresh evaluation; the failed round-4 review cannot be overridden by its earlier completion artifact.
5. **Unknown old attempts stay unknown.** The new epoch has its own attempt namespace. It records prior attempt/replan counts as unavailable and never represents them as zero or as restored history. Any retry-budget policy for the new epoch is stated in the incident decision and cannot be inferred from absent state.
6. **Loss safeguard.** Under a repository-wide lifecycle lock, create and fsync a content-addressed snapshot of the complete `.agent-state` authority tree, including packet revisions and audit records, before replacing the state file. The snapshot manifest binds `state_revision`, `feature_generation`, feature, lifecycle epoch, repository identity, and the archive digest. Maintain per-feature refs plus the repository restore authority `refs/agent-state/current`, which advances only after the atomic state replacement is durable. Restore only the exact full-tree snapshot named by the repository ref and only after verifying its commit, manifest, and every file hash. If the newest referenced snapshot is invalid, do not fall back to an older snapshot; require the new-epoch path. A crash after preparing the snapshot but before state replacement must leave the acknowledged repository ref unchanged. Snapshots survive `git clean -fdx` and branch/worktree operations while the Git common directory remains intact, but not repository/host/disk loss. Do not push refs automatically; an owner must check privacy and explicitly push `refs/agent-state/current` for off-host protection.
7. **Retention.** Keep at most 64 retained snapshots per feature. Never prune the current snapshot or the first snapshot of any lifecycle epoch. Use remaining slots for the newest snapshots; prune older unpinned snapshots only after the new current snapshot is durable. If mandatory pinned snapshots consume the cap, refuse the state commit before replacing `.agent-state` and require an explicit retention review. Snapshot payloads are content-addressed and unchanged files are stored once.
8. **Verification-v2 control store.** `.agent-runs/control/verification-v2` is outside this snapshot. Loss does not recreate lifecycle authority. Existing lifecycle references whose immutable plan, execution, or other authoritative store record is missing fail closed with the existing unavailable/invalid-history errors; the store is not reconstructed from `.agent-state` or evidence. A task with unavailable verification authority must be re-evaluated through the ordinary lifecycle in a new attempt/epoch.
9. **Import binding.** Each imported completion binds the checkpoint, accepted task contract and new packet revision, new epoch, candidate identity, changed-surface seal, accepted spec and verification-contract fingerprints, independent evaluator identity (distinct from builder), and verification-evidence digest. An imported task is eligible only when every dependency in its transitive dependency closure is also imported and independently revalidated in the new epoch. T-009 is always freshly evaluated.
10. **Retry budget.** New-epoch tasks start with `max_rework_attempts: 2` (three total task attempts before escalation), matching the accepted SDD-OBS-001 task policy. Old attempt counts and grants are unknown and never imported. The new epoch does not import human grants; any increase to the numeric budget requires a later explicit owner decision and accepted spec change.

## Proposed task and boundaries

**Task:** Implement explicit recovery of `SDD-OBS-001` into a new lifecycle epoch after authoritative state loss, with a verified evidence baseline, completion revalidation, and a tested loss safeguard.

**Dependencies:** Harness review of the implementation and ordinary Showcase design/verification gates. The old `SDD-OBS-001` lifecycle is not used to execute the recovery task. Recovery execution remains a separate owner-authorized action after implementation review passes.

**Allowed implementation surface:** `tooling/agent-harness/harness.py`, a focused state-snapshot helper and tests, relevant lifecycle documentation, and recovery-feature specification/schema/evidence paths. No edits to old `SDD-OBS-001/evidence/**`; no hand edits to `.agent-state`; no bypass of packet, lifecycle, verification, or evaluator guards.

## Acceptance criteria proposed for the task

- **SR-001:** A missing-state mutation is refused without writing `.agent-state`, except through the explicitly authorized recovery operation. Read-only status does not persist a synthesized state.
- **SR-002:** The incident record is immutable, operator-attributed, identity/fingerprint-bound, and records unknown facts as unknown.
- **SR-003:** The recovery operation verifies the evidence baseline before and after, preserves all existing evidence bytes, and writes only new recovery-epoch records.
- **SR-004:** Old task state is never guessed from ordinary task-completion or human-resolution files. Every imported completion has an independent passing revalidation bound to checkpoint, current accepted contract, new packet revision, and new epoch. T-009's test proves the stale completion and failed round-4 review cannot import it without fresh evaluation.
- **SR-005:** Old attempt and replan counts are represented as unknown; old human resolutions do not authorize new retries.
- **SR-006:** Successful state commits produce verifiable complete snapshots in the separate Git-common-dir namespace and update a pushable ref only after durable state replacement. Fault-injection tests cover each durability boundary, including a crash after snapshot publication and before state replacement; corrupted/missing snapshots; exact restore after deleting only `.agent-state`; retention cap; concurrent commands; and the no-snapshot new-epoch path. No test claims recovery after loss of the Git common directory or host/disk.
- **SR-007:** Independent evaluation challenges byte preservation, task-import binding, T-009 freshness, recovery authorization, concurrent recovery, crash behavior, and the stated backup limit.

- **SR-008:** Import rejects a completion unless its full candidate/spec/VC/evaluator/evidence tuple verifies and its complete dependency closure is independently imported. T-009 cannot pass by importing its historical completion artifact.
- **SR-009:** New-epoch state records a numeric retry budget of two rework attempts per task; imported historical attempts and grants do not change it.

## Implementation review notes

- The new `recover-state` operation is deliberately narrower than `reset` or `migrate-state`: it establishes an empty new epoch only when there is no valid current snapshot to restore. It imports zero historical completions, attempts, packet revisions, or grants; all existing evidence remains archival and tasks begin pending. This avoids treating old completion files as imported work. It means every task must run through the normal lifecycle again, including an independent fresh evaluation of T-009.
- If a valid current snapshot exists, restore it explicitly with `python3 tooling/agent-harness/harness.py restore-state docs/specs/SDD-OBS-001 --expected-snapshot-commit <commit-from-read-only-inspection> --operator <operator-label>`. Restore refuses an invalid/stale snapshot or any existing `.agent-state` directory and restores the exact full tree only when the state root is absent. An invalid newest ref never falls back to an older snapshot.
- If `.agent-state` is absent and `restore-state` reports a prepared snapshot, inspect the named prepared commit and confirm the save was never acknowledged. Then run `python3 tooling/agent-harness/harness.py discard-prepared-snapshot docs/specs/SDD-OBS-001 --expected-prepared-commit <full-prepared-commit> --operator <operator-label>`. The command refuses if `.agent-state` exists, compare-and-swap deletes only that exact prepared ref, and atomically publishes an operator-attributed audit commit under `refs/agent-state-discarded/`. It does not change the acknowledged current snapshot. Afterward, retry `restore-state` against the inspected current snapshot, or use the separately authorized new-epoch recovery path if no current snapshot exists. The operator label is provenance, not authentication.
- New-epoch invocation is `python3 tooling/agent-harness/harness.py recover-state docs/specs/SDD-OBS-001 --epoch-id <new-id> --operator <operator-label> --expected-feature-fingerprint <status-json-value>`. The operator label is audit provenance supplied by the local caller; the harness does not authenticate it. The command requires a committed, unmodified incident record and evidence baseline, a matching repository origin, the observation checkpoint in current history, and all 88 baseline files to match before and after.
- The operation takes the repository-wide lifecycle lock. It writes a content-addressed Git snapshot and prepared ref first, publishes an immutable recovery receipt in `.agent-state/recovery-epochs/<epoch>/`, atomically replaces the new state, and advances the per-feature ref and `refs/agent-state/current` only after the state and receipt are durable. Retrying the same epoch and operator after a successful write is idempotent; any different request refuses to overwrite state.
- If a baseline file changes after recovery, the feature returns to read-only `recovery-required` until an owner resolves the evidence incident. A feature fingerprint change follows the normal lifecycle drift guard.
- The first recovery epoch records the accepted numeric budget `max_rework_attempts: 2`; it does not import old attempt counts or human grants. The verifier control store stays outside this safeguard, as accepted: missing authoritative verification records continue to block through its existing unavailable/invalid-history paths.
- No command has been run against the actual missing Showcase `.agent-state`. Harness implementation review and an owner privacy check of the ref payload are required before the operation or any ref push.
